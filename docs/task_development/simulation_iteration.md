# 仿真迭代与验收

编写阶段先按[常见错误与推荐写法](../../human_experience.md#第一次编写新任务时先避免这些错误)避免已知坐标、状态与资源生命周期问题。规划迭代先用[保存请求的重规划](../user/motion/curobo_diagnostics.md#计时与独立重规划)固定输入，再验证实际动作；不需要每个猜测都重启完整仿真。缓存/碰撞策略改动须有GPU碰撞与净空正反例，不以CPU mock通过代替。

## 何时读取与输入

已有场景、成功条件及可执行 Skill 后读取。输入包括固定开发样本、初态分布、policy 参数和最近失败证据。仿真主要解决可达性、碰撞、阶段衔接、位置泛化和非抓取接触操作，不要求材料完全复刻现实。

## 执行

1. 先逐个验证 Skill，再验证 sub-task，最后从 fresh reset 连续执行完整 Task。组合时传递实际终态，不把独立运行时的理想初态偷偷带入下一段。
2. 正式机器人规划使用 cuRobo，记录实际 backend；已有 MuJoCo 任务由 MuJoCo 执行，外部 benchmark 由其原生环境执行并评分，接入见[原生流程](native_benchmark.md)。CPU IK 对照、纯运动学动画和仿真辅助分别标明。
3. 每次失败定位到具体阶段 / pose，保留目标与实际 FK、误差、起点/目标/路径碰撞诊断、允许接触规则、执行终态和失败视角。未知归因明确写未知。
4. 查看证据、提出原因、做最小修改，再重跑同一失败样本。连续同类失败时增加观测或改变假设，同时回查任务定义、资产和摆位，不能只重复调 IK。严格外部题目中发现环境问题须单独报告，不通过改变题目条件修复成绩；开发诊断可读取的内部信息不自动成为运行时 policy 输入。
5. 稳定后检查规划耗时：区分冷启动、热规划、仿真时长与任务总耗时，报告重试次数；按现有 Motion 接口复用 planner，不为提速静默减少碰撞或安全检查。
6. 在声明分布的固定样本上回归并保留完整分母，开发与最终验收样本分开。恢复能力要用明确失败情形检查：何时恢复、从什么实际状态继续、是否真的完成后置条件，不能把 reset 重跑叫原地恢复。

## 阶段精度与失败回归

编写或迁移Skill前列出阶段目标、路径要求与可接受的平移/转角误差。pre-grasp、自由移动目标和中间点可显式使用预算；关键抓取、击打接触、插入终态保持精确。非接触对齐也必须满足下一步交互的侧向/法向要求。默认严格是兼容行为，开发者应按任务语义配置，不能因默认严格就忽略此项。

预算沿用`MotionRequest.approximate_ik_budget`与现有cuRobo阶段策略，参见[Motion示例](../../gene_agent/motion/README.md)。候选预检要保留预算内但尚需约束重查的候选，不能提前因严格阈值全部丢弃；正式规划仍独立核对碰撞与路径。保存原目标、实际FK目标/关节、误差/预算/approximate标记；后续使用真实执行状态。近似目标通过不表示原目标精确到达，也不解决碰撞或物理失稳。

每轮先在当轮run保存简短记录：`原失败案例/源码与资产版本 → 猜想 → 单一改动 → 要验证的阶段/观测 → 前后事实 → 结论`。原失败改善后再选已成功、双侧/不同臂和工作空间边界的小回归，最后冻结新样本做完整验收。使用旧验收失败调参后，这些样本转为回归，新的独立成功率使用预先固定的新样本。

原生episode可只读比较，无需重跑环境：

```bash
python tools/diagnostics/inspect_native_run.py --run <修改后episode> \
  --compare-with <原失败episode> --stage strike \
  --hypothesis "本轮最小修改应改善的可观察现象" --require-executed --format json
```

物理假设使用`--require-executed`；仅检验规划可行性时不加。不同题目/机器人/seed或身份缺失报`not_comparable`；未进入/未执行目标阶段报`not_tested`。`stage_passed`只表示阶段事实，原任务评分另列；`native_task_succeeded_stage_partial`保留原评分成功但阶段提前结束的事实，完整执行后检查失败则为`native_task_succeeded_stage_failed`。失败代码/来源变化时报告`failure_changed`，不能把规划通过后出现的接触失败称为问题已修复。工具不会自动断言猜想已证实，仍需核对预期观测、有效输入与初态。当前比较适配原生episode格式；其他后端按上述顺序保存证据，不假定可直接套用此CLI。

新原生运行的`development_summary.md`显示实际阶段IK策略和比较入口；旧记录没有策略字段时标未知，并从已保存请求核对，不修改历史run。

原生成功抛出`native_terminated`而尚未完成本项目后置检查时，比较结果为`native_task_succeeded_stage_terminated`（实际partial仍报前述partial），不能冒称Skill终点检查通过，也不能当作工具滑移。执行状态、原始异常和原评分分别保留。

## 查看与运行入口

题目、配置和运行方式从 [benchmarks](../../benchmarks/index.md)选择。具体 Skill / Task 使用[共享操作工作流](../user/visualization/shared_operation_workflow.md)和[检查说明](../user/visualization/skill_viser_inspection.md)。

`tools/viewers/view_skill.py` / `view_task.py` 会根据参数分派到在线规划或已有 run 回放等路径，不能笼统称为纯视觉或实际仿真。交付时必须说明本次入口的来源与模式；查看已有记录不等于重新执行任务。

当前 MuJoCo 任务的视频使用[统一视频反馈入口](../user/visualization/video_feedback.md)。原生 benchmark 可直接保留实际原生 MP4 与时间/阶段索引，公共分派适配尚待实现，不为录像转换到 MuJoCo。相机需要看清全景、目标接触和能同时看见两指的夹爪侧面；不能用遮挡关键部位的大量 overlay 替代有效证据。

## 交付与完成条件

交付输入/代码/资产版本、有效参数、逐阶段结果、失败类型、成功率分母、耗时、恢复结果与可查看的运行目录。简短结论应让用户知道做了什么、哪里失败、下一步做什么；原始 JSON 留在 run 内供定位。

已有自建任务在允许且记录双侧有效接触后使用辅助夹持，必须标为仿真辅助成功，并在松爪时释放；严格外部 bench 沿用原条件，不据此额外添加辅助。规划 attachment 不证明物理夹持。微波炉历史混合仿真证据见[任务说明](../user/microwave/mujoco_task1_physical.md)，不能直接外推到新资产、分布或真机。

## 失败处理

按[人类经验](../../human_experience.md)区分直接原因与根本原因。仿真中自主查方案，较难问题可借助 Astra（当前环境可用时）；重要的任务语义或条件变更向用户说明。完成一轮后提出值得保留的经验或工具改进，与用户讨论后再固化，不能把一次成功经验无条件泛化。

规划失败排查入口：[cuRobo诊断](../user/motion/curobo_diagnostics.md)。区分起点、目标IK和路径；正式结果与旁路诊断分开，诊断异常不覆盖原始失败。
