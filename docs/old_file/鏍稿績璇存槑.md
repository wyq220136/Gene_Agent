# Gene_Agent 核心说明

这份文档面向人，说明项目要解决什么问题、怎样开发和怎样判断结果。它记录的是长期目标与工作原则，不把尚未完成的能力写成现状。给开发 Agent 的具体约束见 [AGENTS.md](AGENTS.md)，当前运行入口见 [README.md](README.md) 与 [tools/README.md](tools/README.md)。

## 目标与最终效果

1. **快速部署新任务。** 人提供或确认资产、相机与物体摆位、操作意图和必要的参数；Codex 主要负责组合已有模块、开发缺失 Skill，并根据结构化错误和视觉反馈自主迭代。新任务不应迫使我们复制整套执行流程。
2. **针对场景提高成功率。** 可以为特定场景调整操作知识、物体摆位和 Skill 参数，同时在声明的物体位姿扰动范围内保持高成功率。成功率应由固定样本、明确判定函数和完整分母给出；单次成功、好看的动画或一次截图不代表鲁棒性。连续多次成功（例如连续 10 次）也是需要单独验收的目标。
3. **仿真先行，少量真机调试。** MuJoCo 用来发现可达性、碰撞、阶段衔接和接触问题，不必精确复制采集场景的每一处物理细节。若仿真抓取几何和双侧接触已确认，但资产摩擦误差导致后续滑落，可在记录接触证据后启用可关闭的仿真特权固定，并在放置时释放；这种结果必须标为“仿真辅助”，仍需验证碗的位置、姿态与门/桌面碰撞，不能冒充纯物理或真机抓取。仿真中形成的操作逻辑应尽量复用到真机，再针对感知和物理差异调整。

微波炉任务的目标效果以 [goal_effect.mp4](data/goal_effect.mp4) 为参考，并增加旋转按钮动作。这是目标演示，不表示所有动作目前已经在仿真或真机实现。当前优先检查抓碗、抓把手开关门、推门和 `knob_0`；各动作要能单独调试，再组合成长程任务。

## 方法：从场景表示到任务执行

```text
资产、机器人模型、物体实例与位姿
          ↓
Concept：物体和部件的结构化几何、坐标及参数
          ↓
Knowledge：参数化抓取候选、旋钮/门的操作几何
          ↓
Skill：选择目标，组织接近、操作、退出等阶段及失败处理
          ↓
Motion planner：IK、路径、直线 TCP 运动与逐阶段碰撞约束
          ↓
Task：按顺序组合 Skill，传递每一步执行后的实际状态
          ↓
MuJoCo / 真机执行 → 状态、错误、图像与视频反馈
```

Knowledge 通过用户给定的参数范围和必要的后处理规则，产生可解释的局部操作候选，再结合当前物体位姿变换到世界坐标；它可以调用抽象 IK 接口筛选目标 pose 的可达性，但不应绑定 cuRobo，也不把路径或碰撞成功混入“纯 IK 可解”。Skill 使用 Knowledge 与 motion 的能力，不复制求解器。Task 组合 Skill；下一步应读取上一步实际执行后的状态，不能暗中重置或沿用过时的物体位姿。当前仿真开发默认使用 GT 场景状态；未来接入 FoundationPose 与 mesh 重建时，应保持下游状态语义一致。

对抓碗尤其要区分：候选抓取 pose 可达、`pregrasp → grasp` 直线接近可规划、夹爪实际接触、抬升保持成功，是不同的结论。抓取目标无解时，应同时检查 Knowledge 参数、物体相对机械臂摆位、机器人/TCP 配置和规划约束。为找到可达解可以合理移动物体或修改操作知识，但不能通过忽略必要碰撞或改变成功标准制造“成功”。

## 新任务的准备与迭代

1. **确定任务与摆位。** 人先大致规定物体相对机器人、相机的摆放，以及要完成的动作。当前先用已验证的 Realman 配置；架构应支持其他单臂、双臂及夹爪，但跨型号能力必须另行验证。
2. **准备资产和结构。** 准备 mesh、规划碰撞代理、MuJoCo 接触几何、部件参数与机器人 URDF。必要时用 SAM3D、ArtiCraft 等工具辅助重建；部件标注现阶段可由人完成。visual 尽量像实物，collision 可以简化，但必须检查尺度、原点、link 和可动关系。
3. **构建仿真场景。** 用相机标定和真实照片确定参考关系，在 MuJoCo 中得到合理、无初始穿透的场景。采集位置只是参考：桌面高度、微波炉和物体位置可以为可达性与稳定接触显式调整，并记录调整后的名义 pose。
4. **定义 Skill 与判定。** 人先用自然语言描述任务分解和注意事项；为每个子任务写明确的成功/失败判定。声明允许扰动的物体、坐标系、范围和随机种子，区分无效初态与操作失败。
5. **在仿真中迭代。** Codex 调整候选、阶段目标、规划及恢复逻辑；参数搜索可以并行，但必须共用场景样本与判定标准。每次改动记录配置、场景版本、失败阶段、规划耗时、碰撞对象和可复查画面；必要时让人通过 Viser 点选候选或拖动/输入参数，再保存结果继续自动开发。
6. **迁移到真机。** 先复用经过仿真验证的 Knowledge、Skill 和任务顺序，再处理感知误差、夹持深度、摩擦和安全作用力等差异。真机动作需要独立安全检查，不能从仿真成功直接推断真机成功。

## 反馈必须帮助找到原因

原子 Knowledge、单个 Skill 和完整 Task 都应可独立检查。后台接口应提供可机器读取的摘要与完整日志；Viser、MuJoCo 是同一状态和运行记录的两种检查视图，不能各自维护一套操作事实。人能看见的错误原因，Codex 也应能从记录与截图中获得。

检查界面或证据包至少要能回答：当前目标与实际 pose 是什么；机器人、夹爪、物体坐标轴朝向如何；哪些物体、碰撞代理和 attachment 被规划器使用；失败在 IK、路径、直线接近、执行还是任务判定；若路径因碰撞失败，是自身还是哪个场景物体；每阶段的耗时与轨迹是什么。终端突出关键原因，原始返回值、traceback 和状态仍完整保存。原因尚不确定时明确写“未知”，不要臆测。

相机视角要能看见全景、目标、夹爪侧面和关键接触；坐标轴与相机参数要可检查。自动截图工具应真正读取图像，必要时录制完整 Skill 及其各阶段的视频，不能只凭文件存在就说视觉验收通过。本地 Linux 上人可优先用 MuJoCo 交互检查；Viser 尤其适合远程、人机协同调参和 Codex 截图分析。

## 仿真与现实的两类差距

- **感知：** 仿真 GT 与真机 Foundation Model 的分割、位姿估计不同。相机摆位要保证可见性；必要时添加规则和不确定性处理，操作逻辑也应容忍一定 pose 误差。感知模块可以晚于 GT 仿真接入，但真实任务不能把 GT 当成实际观测。
- **物理：** 夹爪抓多深、是否双侧接触、碗是否滑移，以及机械臂对物体施力过大等问题，很难仅靠运动学动画判断。MuJoCo 可提供接触诊断，真机仍需用真实传感和保守控制验证。

过去开发慢，主要因为空间关系缺少视觉反馈、问题要多次真机运行才能发现、旧代码和配置过于分散；IK 无解也常由摆位或操作知识引起。这些经验要求我们持续精简模块、优先补足诊断和可视化，同时保留旧项目中已验证的数值、坐标和规划细节。旧文档可能过时，应以实际代码、资产、测试和实测记录交叉核对。

## 当前边界与后续方向

截至 2026-10-07，项目已有 GT 场景、Knowledge/Viser 检查、cuRobo 规划和 MuJoCo 抓碗单场景物理验收；门与 `knob_0` 有独立的运动学规划检查。这些不等于微波炉完整任务、位置分布成功率或真机效果均已验收。当前可执行命令与证据见 [README.md](README.md)、微波炉摆位检查（历史材料已本地归档；当前入口见 index.md） 和 [目录迁移记录](docs/developer/maintenance/code_layout_migration_log.md)。

后续重点是：把各 Skill 可靠地组合成微波炉任务；在固定扰动分布上评估与调参；继续改善错误归因、碰撞与接触视频；用新增食物检验任务部署速度，再做 sim2real。其他长程、精细、双臂、语义、非抓取和动态任务可作为后续能力测试，不应抢占当前微波炉基线的验收。

可参考仓库内的 `third_partys/EmbodiedSWE`、`third_partys/graph-as-policy` 和 `third_partys/ASPIRE` 学习自动迭代与反馈组织；只借鉴经本项目验证有用的机制，不照搬完整框架。
