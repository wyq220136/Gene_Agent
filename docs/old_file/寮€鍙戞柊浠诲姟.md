# 新任务配置指南

本文用 task_1 的“微波炉 + 盘子 + 碗”任务说明新增任务的一般流程。详细命令以
各模块 README 和 [`docs/commands.md`](commands.md) 为准。

暂时不涉及到如何添加新的geometry， 只支持ring, cuboid, cylinder, trifold cuboid, cuboid container五种geometry

注意不要把相机外参复制错了。如果使用右臂直接标定，把extrinsic_parameter对应的参数读取出来

## 扩展到新的 Robot 与 Gripper：单臂 Realman＋Pika 示例

新任务不一定沿用双臂 Realman 和原夹爪。仓库已有显式的
`realman_single_pika` 配置：正装单臂、没有双臂身体底座，保留 Realman 七轴，
将 Pika 原始 URDF 的双指关节装到 `link_7`。它目前是**仿真与规划基线**，
不能仅凭能显示模型或规划短轨迹就认定 Skill、完整 Task 或真机可迁移。

换机器人/夹爪时，按同一条链逐项核对：

1. **资产与安装。** 提供机械臂和夹爪 URDF、visual/collision mesh、关节限位，
   在独立 profile 中声明 `T_world_base`、`T_link7_gripper_base`、
   `T_gripper_base_tcp`、活动臂组和关节顺序。Pika 示例的配置在
   `config/robots/realman_single_pika.json`，装配和 MuJoCo 元数据由
   `gene_agent/robots/realman_pika.py` 生成。配置中的 Pika 法兰平移与 TCP
   是暂定值；已确认的是零位装配方向，不能把视觉对齐当成实物标定。
2. **控制与状态。** 验证 MuJoCo 中各指关节的开合方向、实际指内面宽度、
   指垫接触、TCP 和关节零位；Skill 应通过机器人元数据取得当前活动臂与
   夹爪命令，而不是写死双臂或旧夹爪宽度。物体 pose、接触和执行终态
   仍须来自同一次仿真状态。
3. **cuRobo 几何与坐标。** 用同一装配 URDF、base、`link_7` 到 TCP 变换和
   关节顺序建立规划配置。区分外观 mesh、MuJoCo 接触几何与 cuRobo
   `collision_spheres`：一个 STL 文件不会自动成为规划时实际使用的碰撞体。
   Pika 当前由 `gene_agent/motion/curobo/profiles/pika.py` 读取三个原始 STL，
   为各 link 生成 AABB 外接球，再把当前 MuJoCo 指关节位置锁入规划快照；
   开口改变后要重新导出快照。检查球是否覆盖手指和掌部、是否误占抓取
   净空，以及相邻 link 的 self-collision 排除和物体 attachment。
4. **从小到大验收。** 先看零位模型、底座 XYZ 与张合；用多组关节角对比
   MuJoCo/cuRobo 的 FK 和 TCP；再测已知碰撞与已知净空、短距离连续轨迹，
   最后在指定物体位姿上跑单个 Skill、MuJoCo 接触和完整 Task。每层分别
   记录成功或失败，不能用短路径成功代替抓取成功。

本地可复现的两个起点（`curobo` conda 环境，不控制真机）：

```bash
MUJOCO_GL=egl conda run --no-capture-output -n curobo python tools/viewers/capture/render_realman_pika_preview.py
MUJOCO_GL=egl conda run --no-capture-output -n curobo python tools/diagnostics/check_realman_pika_motion.py
```

第一条生成 `runs/realman-single-pika-preview/zero_overview.png`、
`zero_base_axes.png`、`pika_close_40mm.gif`；第二条核对四组 FK/TCP、
一段短轨迹和两个定点碰撞探针。抓碗诊断入口是
`experiments/probes/check_pika_pick_bowl.py`，但已有记录中碗在抬升后滑落，
不能把它写作 Pika 抓取已通过。详见
`docs/tmp/history/developer/realman_pika_profile_plan.md`。

**相对旧项目仍需补齐的部分。** 旧项目
`AffordToolAct/robots/realman/gripper_collision.py` 和
`AffordToolAct/scripts/tools/gripper/generate_long_gripper_collision.py`
能按开口、长度和厚度生成**延长夹爪**的 collision STL 与保守碰撞球，
`AffordToolAct/robots/realman/curobo_assets.py` 再将球作为附加 link 注入
cuRobo，并能在 Viser 对照显示 mesh/球。那套几何针对旧延长夹爪，
**不是 Pika collision 文件**，不能直接复制尺寸和 frame。新项目已有
Pika 原始 URDF/mesh 与运行时生成的 cuRobo 外接球，但还没有等价的
Pika 专用、可调的简化 collision mesh 生成及 mesh/球对照审计流程；
应先明确真实接触面、开口变化、link 局部坐标与误差预算，再按需制作
简化 collision mesh 或球，比较
覆盖和净空样例，不能只生成 STL 就宣称规划碰撞完成。Pika 的法兰/TCP
实物标定、接触参数、抓碗稳定性，以及更高层 Skill/Task 的跨 profile
验收也尚未完成。旧仓库只作行为、资产与数值参考，不在旧仓库直接修改。

## 1. 准备任务数据

**自动构建场景可以参考  docs/user/scenes/reconstructed_tabletop_scene.md**

先采集同一帧 RGB-D 和相机参数，再按统一目录保存物体：

```text
data/<task>/
├── rgbs/、depths/、camera/
└── objs/<Category>/<Instance>/
```

例如：

```text
objs/Bowl/Bowl_0/
objs/Plate/Plate_0/
objs/Microwave/Microwave_0/
```

已有物体可以复用 mesh 和 Concept，但如果换了 RGB-D 帧，mask 和 pose 仍需重新验证。

**注意，准备物体用于分割和位姿估计的mesh的时候，需要确认它们能被鲁棒的估计位姿。这里的选择有一些技巧，比如当前估计微波炉的pose使用的仅仅是handle的mesh，通过Handle推理出其他的part。而且利用门板的平面信息对handle的姿态做了一个修正。**

## 2. 分割并生成物体 mesh

每个新增物体都需要独立 mask 和文本 prompt。以 Plate 为例：

```bash
# sam3
curl -X POST http://127.0.0.1:18080/segment \
  -H 'Content-Type: application/json' \
  -d '{"image_path":"data/task_1/rgbs/rgb_0.png","items":[{"category":"Plate","prompt":"green plate","mask_path":"data/task_1/objs/Plate/Plate_0/masks/mask_0.png"}]}'

# SAM3d
PYTHONPATH=. python perception_modules/recon_3d/recon_client.py \
  --object-dir data/task_1/objs/Plate/Plate_0 \
  --server http://127.0.0.1:18083 \
  --simplify-mesh --visualize
```

先检查 mask 是否只覆盖目标物体，再检查 RGB-D 点云与 SAM3D mesh 是否一致。 然后把obj_mesh_simplified.obj复制改名为obj_mesh.obj

## 3. 用 primitive 标注结构

**concept不用把物体表示全，比如可以使用一个ring来表示杯子沿，忽略杯子的底部**
**hint: 可以用scripts/concept/visualize_task0_concepts_open3d.py来查看当前的标注是否准确**

Concept 只描述物体几何，不负责机器人动作。优先使用已有 primitive：

- 盘沿、碗沿：`RingPrimitive`；
- 旋钮：`CylinderPrimitive`。

使用现有 Concept 可视化工具，将 primitive 与物体局部 mesh 叠加，通过调整尺寸和
`pose_matrix` 检查标注。以 Plate 为例：

```bash
PYTHONPATH=. python visualization/knowledge/viser_concept_tuner.py \
  --mesh data/task_1/objs/Plate/Plate_0/meshes/obj_mesh_simplified.obj \
  --template RingPrimitive \
  --output data/task_1/objs/Plate/Plate_0/conceptualization.json
```

标注完成后保存为物体的 `conceptualization.json`。

**这块要用尺子量一下尺寸**

微波炉有多个旋钮时，为每个旋钮建立独立的 `Cylinder` item，并用 `component`
区分，例如 `knob_0`、`knob_1`。直径 5.5 cm、高 1 cm 对应的初始 `size` 为
`[0.0275, 0.0275, 0.01]`；前两个值是半径，可以在 tuner 中继续微调。以 Microwave
为例：

```bash
PYTHONPATH=. python visualization/knowledge/viser_concept_tuner.py \
  --mesh data/task_1/objs/Microwave/Microwave_0/meshes/obj_mesh.obj \
  --concept data/task_1/objs/Microwave/Microwave_0/conceptualization.json \
  --output data/task_1/objs/Microwave/Microwave_0/conceptualization.tuned.json
```

在界面中分别选择两个 knob，调整各自尺寸和局部 `pose_matrix`，确认后再用调参结果
替换正式的 `conceptualization.json`。该命令不带 `--task-dir`，因此只显示局部 OBJ；
需要与真实点云对齐时使用第 4 节的流程。

注意：调参和后续几何检查应使用已烘焙 SAM3D scale 的
`obj_mesh_simplified.obj`。运行感知流程前，确认物体目录下的 `obj_mesh.obj` 已替换
为同样的实际尺寸版本。primitive 的 pose 属于物体局部坐标系，不要把相机坐标系下
的 mesh 或 pose 再次当作局部数据使用。

## 4. 用 FoundationPose 验证感知

FoundationPose 使用当前帧的 RGB-D、mask 和已应用实际尺寸的物体 mesh 估计物体
pose。mesh 生成完成后，验证阶段不要再次调用 SAM3D。以 Plate 为例，运行单物体
感知入口，完成“采集 RGB-D → SAM 分割 → FoundationPose → 点云可视化”：

```bash
PYTHONPATH=. python perception_modules/run_single_object_perception.py \
  --task-dir data/task_1 \
  --category Bowl \
  --object-dir data/task_1/objs/Plate/Plate_0 \
  --prompt "blue bowl" \
  --camera-endpoint tcp://127.0.0.1:18082 \
  --seg-server http://127.0.0.1:18080 \
  --pose-server http://127.0.0.1:18081 \
  --side right \
  --visualize
```

该入口使用物体目录下的 `meshes/obj_mesh.obj`，并将结果保存到
`pose.json`。验证时应同时查看估计 pose 下的 mesh 与真实点云，而不是只检查数值
输出。注意：该命令会重新采集并覆盖任务目录中的 `rgb_0.png`、`depth_0.png` 和
相机参数。

需要批量感知时，在 `perception_modules/segmentation/category_config.py` 中为每个
类别配置 SAM prompt。例如本任务使用：

```python
"Plate": {
    "masks": [{"prompt": "green plate", "suffix": ""}],
},
"Bowl": {
    "masks": [{"prompt": "blue bowl", "suffix": ""}],
},
```

然后可一次处理多个类别：

```bash
PYTHONPATH=. python perception_modules/run_task_perception.py \
  --task-dir data/task_1 \
  --categories Microwave Plate Bowl \
  --camera-endpoint tcp://127.0.0.1:18082 \
  --seg-server http://127.0.0.1:18080 \
  --pose-server http://127.0.0.1:18081 \
  --side right \
  --visualize
```

微波炉可以继续使用把手 mesh 和把手 mask 估计 Microwave 的父 pose。新增旋钮时，
先在 Microwave 局部坐标系中标注：

```text
T_camera_knob = T_camera_microwave @ T_microwave_knob
```

再检查变换后的 Cylinder 是否与真实点云中的旋钮位置一致。

单独验证 Microwave 时，先用把手 prompt 和 `handle_mesh.obj` 估计父 pose。不要加
`--visualize`，避免先打开独立的 Open3D 窗口：

```bash
PYTHONPATH=. python perception_modules/run_single_object_perception.py \
  --task-dir data/task_1 \
  --category Microwave \
  --object-dir data/task_1/objs/Microwave/Microwave_0 \
  --prompt "red handle" \
  --camera-endpoint tcp://127.0.0.1:18082 \
  --seg-server http://127.0.0.1:18080 \
  --pose-server http://127.0.0.1:18081 \
  --side right \
  --visualize

 PYTHONPATH=. python perception_modules/run_task_perception.py \
    --task-dir data/task_1 \
    --categories Microwave \
    --camera-endpoint tcp://127.0.0.1:18082 \
    --seg-server http://127.0.0.1:18080 \
    --pose-server http://127.0.0.1:18081 \
    --side right \
    --visualize
```

然后启动 tuner，加载同一帧点云和刚生成的 `pose.json`。OBJ 和 knob 都挂在
FoundationPose 估计的 Microwave 父 frame 下，滑块调整的仍是 knob 的局部 pose：

```bash
PYTHONPATH=. python visualization/knowledge/viser_concept_tuner.py \
  --mesh data/task_1/objs/Microwave/Microwave_0/meshes/obj_mesh.obj \
  --concept data/task_1/objs/Microwave/Microwave_0/conceptualization.json \
  --output data/task_1/objs/Microwave/Microwave_0/conceptualization.tuned.json \
  --task-dir data/task_1 \
  --max-points 30000 \
  --max-depth 3.0
```

`--max-points` 控制确定性下采样后的最大点数。点云不是必需的；省略
`--task-dir` 即回到纯 OBJ 调参模式。只有点云模式会自动把 Viser 相机聚焦到
Microwave，并显示“聚焦 Microwave”和“聚焦当前 Concept”按钮；选择某个 knob 后
可用后一个按钮进入近距离调参视角。纯 OBJ 模式不修改 Viser 相机设置。


**hint: 写操作knowledge的时候，要确保能生成足够多样的动作(比如允许gripper绕着局部x/y轴旋转)，或者让物体摆放的位置比较合理，这样**
**hint: 可以留意一下有没有现有的knowledge或者skill，按理说，比较基础的功能是已经实现过的了**

## 5. 编写 Knowledge

本节到第 7 节按 **Gene_Agent 当前代码**编写；上面第 1～4 节仍保留了旧项目的感知与 Concept 操作记录，其中的 `perception_modules/`、`visualization/knowledge/` 等命令尚不是本项目入口，不能直接照着运行。旧项目《运行指南》的原文副本见 [旧版运行指南](docs/reference/affordtoolact_run_guide.md)。它用于核对已验证的操作顺序和参数，不代表这些脚本已迁入 Gene_Agent。

Knowledge 接收已标注的 Concept、物体世界 pose 和任务目录中的参数，输出**有序的抓取候选或操作目标 pose**。它应说明目标所属的局部坐标系、轴的正方向、单位、候选来源及参数；抓取候选还带有建议的夹爪闭合宽度。门轴由用户显式提供，不从 Concept 推断。Knowledge 可以调用抽象 IK 接口检查单个 pose 的可达性，但纯 pose IK 不检查场景碰撞、连续路径或物理接触；失败和近似候选也应保留原始目标与实际 FK 误差供后续判断。

抓取时先选合适的 Concept 和 generator，再为**具体任务中的物体实例**设定候选范围、顺序与必要的 pose 后处理。当前支持 `ring`、`cylinder_axial`、`cylinder`、`cuboidal_block`、`trifold_handle`。例如碗沿使用 `ring` 的方位角与局部倾角候选，旋钮使用 `cylinder_axial`；不要把示例数值当作所有新物体的默认值。`data/task_1/knowledge/grasp_profiles.json` 是 task_1 的 Knowledge 配置示例，包含 `parameters`、`closing_width`、`postprocess` 等字段。这里的 `depth_m` 若出现，是特定 generator 的几何位移参数，不是统一的“抓取深度约束”。`pregrasp` 距离或开口、运动速度、碰撞策略和规划重试属于 Skill／Motion，不能塞进 grasp profile。

在 `curobo` 环境及项目根目录，可先分别检查抓取公式、当前支持的对象 profile 和微波炉操作 Knowledge：

```bash
python tools/editors/view_grasp_knowledge.py --kind ring
python tools/editors/tune_grasp_profile.py --profile task_1_bowl_0
python tools/editors/view_microwave_knowledge.py --mode door_push --ik-backend curobo
```

`view_grasp_knowledge.py` 可切换上述五类 generator；`tune_grasp_profile.py` 当前只内置 `task_1_bowl_0`、`task_1_knob_0` 和 `trifold_handle` 三个示例，不是任意新物体的通用编辑器。它默认将调参结果保存到 `data/task_1/grasp_profiles.tuned.json`；检查后再明确更新正式 profile，不能把试算结果自动视为已验收配置。微波炉页面还可选 `handle_grasp`、`handle_pull`、`door_push`、`knob_grasp`、`knob_turn`，能查看候选、参数、目标夹爪和纯 IK 诊断；其中 cuRobo IK 使用空场景障碍，**不能**据此宣称门、桌面或旋钮无碰撞。具体操作见 [微波炉 Knowledge 调参](docs/user/microwave/microwave_knowledge_viser.md)。

新任务的 Knowledge 验收至少要保存：所用 Concept／profile、生成的候选数量与顺序、选中候选的完整 TCP pose、局部到世界的变换、夹爪开口、可选 IK 结果和可复现的截图。若 IK 常失败，先核对坐标与物体摆位，再检查参数范围和局部 X/Y 倾角；不应直接放宽碰撞或把近似解写成严格成功。

## 6. 编写 Skill

运动规划的推荐调用方法见 [Motion使用入口](gene_agent/motion/README.md)：Skill接收
StageMotion，应用层准备当前状态/场景并管理session；默认复用solver和CUDA Graph。

Skill **复用 Knowledge 的候选和操作目标**，根据当前场景与机器人状态组成动作阶段，再向抽象 Motion Planner 请求 IK、普通路径或 `linear_tcp` 路径。`Pick` 是抓取阶段的组合；pregrasp、pre-contact、接近、撤离、开合夹爪、候选选择、阶段失败处理属于 Skill 或相邻 Task 编排，不应在 Knowledge 中复制一套。Task 负责 Skill 的顺序、跨段状态交接和任务后置条件；具体物体或微波炉的装配代码放在 `gene_agent/applications/`，通用逻辑留在 `gene_agent/skills/` 和 `gene_agent/motion/`。

每个阶段都要显式说明并记录以下内容：起点与目标 TCP／关节状态，路径类型（普通规划或 TCP 直线），选中的 Knowledge 候选，参与碰撞检查的物体与机器人几何，允许的接触对，夹爪命令，attach／detach 时点，以及规划结果和执行后的状态。以抓取为例，pregrasp 通常保持完整场景碰撞；靠近碗沿的直线接近只允许**本阶段确有必要的指尖—目标接触**；闭爪后才能建立规划 attachment，放手后要更新物体 pose 与碰撞场景。不要把“忽略桌面”“忽略目标物体”写成整个 Skill 的默认规则，也不能凭视觉接近就宣称物理夹紧。门的 pre-contact 同样在选定首个 contact 候选后按门面朝外法向生成；实际接触从 contact 阶段才启用对应白名单。

对抓紧、放置或其他关键终态保持严格检查。推门、pre-contact、pregrasp 等非关键目标若允许近似 IK，必须由该阶段明确设置位置／姿态误差预算，同时报告原目标、实际 FK TCP、误差及碰撞／关节约束结果；后续规划仍基于被接受的实际姿态并做整条轨迹碰撞检查。要求 TCP 直线的段不能在失败时静默改成曲线。规划失败应保留已完成阶段和原始后端诊断，不能从初始 joint 偷偷重规划后冒充连续执行。

当前单个 Skill 的在线**纯视觉规划**入口如下；页面顶部可切换其他已接入的 Skill，编辑并应用摆位后会重新生成目标和碰撞场景、再规划连续轨迹：

```bash
python tools/viewers/view_skill.py --skill pick_bowl
python tools/viewers/view_skill.py --skill handle_pull
python tools/viewers/view_skill.py --skill push_open
python tools/viewers/view_skill.py --skill rotate_knob
```

现有选项还包括 `push_close`、`insert_bowl`、`extract_bowl`、`place_bowl`。页面应逐阶段核对轨迹、规划时间、失败原因、碰撞对象／允许接触和 attach 状态。`view_skill.py` 会**现场规划**，不等同于历史 run 回放；视觉轨迹也不等于 MuJoCo 物理执行。新物体或新机器人若尚未接入这些页面，需要先增加对应场景／Skill 适配并单独验收，不能仅添加一个 profile 就声称可用。

## 7. 在仿真中开发 Task

先用 GT 场景开发，不等待感知模块接入。任务目录同时保存 Knowledge、Skill 与场景参数，但字段职责分开；以 `data/task_1/` 为当前例子，不把它的固定路径或 Realman 参数写成通用框架默认值。记录物体／机器人初始 pose、门和旋钮关节状态、桌面尺寸、使用的 visual、MuJoCo 接触几何与 cuRobo 碰撞代理。改变物体或微波炉摆位时，应同步更新 Concept 世界 pose、操作目标、门关节、碰撞快照，再从**同一新初态**重新规划。允许围绕名义摆位设定扰动范围，但要保留范围、坐标系、采样 seed、有效初态规则以及失败样本。

### 7.1 先验收单个 Skill，再组装子 Task

先检查抓取、拉把手、内侧推开、外侧推关、放入、取出／桌面放置和旋钮各自的 Knowledge 与 Skill；再按执行后的实际状态拼接。当前在线纯视觉子任务包括 `microwave_door_open`、`microwave_door_close`、`microwave_door_cycle`、`microwave_object_insert`、`microwave_object_extract` 和 `microwave_knob_rotate`。例如：

```bash
python tools/viewers/view_task.py --task microwave_door_cycle
python tools/viewers/view_task.py --task microwave_object_insert
python tools/viewers/view_task.py --task microwave_object_extract
```

门的旧版权威行为以复制的《运行指南》中 `run_microwave_task1.py --door-only` 的**实际调用链**为准：先抓把手拉到约 25°，再从门内侧推至目标角度；关门从外侧推，不倒放开门轨迹，也不重新抓把手。25° 和最终开门角是可调目标；把手松开、推门 pre-contact、接触白名单与返回默认 TCP 的阶段顺序都要在子 Task 中核对。纯视觉页面可输入推门起始角来复现重新测得的门角，但不会进行真实感知。

放入碗沿用相对微波炉的固定 TCP keypose：`pre_place → place → 松爪／detach → post_place_1 → post_place_2`。取出使用 `pre_extract_1 → pre_extract_2 → extract → 闭爪／attach → post_extract_1 → post_extract_2`，然后在桌面放置。抓取后用实际 `T_tcp_object` 计算附着关系；放置目标不能直接写死碗的世界 pose。当前 `data/task_1/knowledge/microwave_object_manipulation.json` 中的 keypose 来自**旧微波炉 frame**；在现有校准 URDF 上使用前必须通过 `object_frame_alignment` 对齐，不能把相同数字直接当成当前 URDF root 下的 TCP。可用以下命令查看几何叠图；它的报告明确标为仅预览，不代表轨迹可规划：

```bash
python tools/viewers/inspect_microwave_object_keyposes.py
```

### 7.2 再验收完整 Task 的连续规划

当前 `microwave_task1` 的纯视觉顺序为：第一次开门 → 抓碗并放入 → 关门 → 旋转旋钮 → 再次开门 → 取碗并放到桌面 → 关门。旋钮是当前七段视觉编排的一段；其画面中关节角更新不证明夹爪对旋钮施加了物理作用。要检查明确的 **25° 拉门、推门至 90°** 路径，使用下面的配置；旧 `task1_visual_legacy85_verified.json` 在拉门后直接把门状态设为 85°，不包含内侧推门轨迹，不能替代此项验收。

```bash
python tools/viewers/view_task.py --task microwave_task1 \
  --config data/task_1/visualization/task1_visual_explicit90_verified.json
```

Task 页面可逐分区查看真实规划轨迹及状态交接。编辑场景后先应用新摆位再重规划；核对下一段是否从上一段的实际终态出发，而不是重置机器人、门角、碗 pose 或 attachment。验证失败要保留失败阶段、原始目标与实际 FK、起点和目标碰撞、碰撞对象、自碰撞、路径搜索结果、规划时间以及不能归因时的原始证据。`goal_ik_no_solution` 不能自动解释为某个物体挡住；`start_collision`、`goal_collision`、`path_collision` 与 `path_not_found` 也须依据本次诊断分别判断。

需要给人或 Codex 复核视觉结果时，可录制在线规划产生的轨迹并检查同名 JSON 清单：

```bash
python tools/viewers/recording/record_visual.py --kind skill --name rotate_knob --camera gripper_side
python tools/viewers/recording/record_visual.py --all --fps 6
python tools/diagnostics/check_visual_acceptance.py
```

视频、截图和清单的用法见 [在线视觉检查说明](docs/user/visualization/viser_skill_task_debugging.md)。录像或 Viser 规划成功，只证明当前 GT 场景下的运动学目标、连续规划和视觉状态检查通过，**不证明**门的物理接触、碗稳定夹持、旋钮受力或完整任务的物理成功。

### 7.3 用 MuJoCo 验证物理结果与位置泛化

对每个 Skill 分别检查实际接触顺序、门／物体运动、夹爪开合、碗口朝上与 release 后终态；再从同一次 MuJoCo 状态连续执行子 Task 和完整 Task。当前已有从 fresh reset 连续执行的 [Task1 混合仿真验收](docs/developer/microwave/evidence/mujoco_task1_mixed_acceptance_2026-10-13.md)，入口为 `python tools/run/run_microwave_task1_physical.py`。门由接触带动；碗在双侧指垫接触后使用可追溯的仿真辅助夹持；旋钮末端采用运动学角度提交。因此它证明名义摆位的连续混合仿真流程，不是无辅助的全物理成功，也不代表位置泛化或真机成功。`view_skill_mujoco.py` 只读取已有物理 run 并显示 `actual` 或 `planned`，不会在线执行 Skill。

调参时先固定一组可复现的名义摆位和失败样本；再针对声明的位姿扰动逐 seed 检查规划、接触和任务后置条件，统计成功率与失败类型。仿真不必复刻所有真实材料属性：如果抓取几何和双侧指垫接触已证实，而资产摩擦使碗滑落，可显式记录并启用可关闭的仿真辅助固定，在松爪时解除；结果应标成“仿真辅助成功”，不能当作自然物理抓取或真机成功。真机部署、感知与标定将单独写在第 8 节；本节不提供旧项目真机命令。

## 8. 在真机部署 Task

代码位置：设备、感知、实测状态与执行检查位于 `gene_agent/realworld/`；本任务的现场适配位于 `realworld/microwave/`，独立子任务和完整任务共用 `task.py` 的操作入口。不要再在 `applications/microwave/` 新增 `realworld_*` 文件，也不要为真机复制 Knowledge/keypose 算法。目录及现有共享边界见真机代码整理说明（历史材料已本地归档；当前入口见 index.md）。

真机代码集中在 `gene_agent/realworld/`。第 7 节已调好的 Knowledge、Skill 目标、Task 顺序及 motion 请求是起点；**现有仿真和 Viser 调用链先保持不变**。真机不直接运行 `Task1VisualSession` 或 MuJoCo 的 `CuroboRuntimeBridge`：它们使用仿真模型和 GT 状态。真机每段需要读取当前关节、物体与门的实测状态，构建现场碰撞快照，按同一 Skill 语义重新规划，再执行并检查实际后置条件。不要把纯视觉轨迹、MuJoCo 接触或仿真辅助夹持称为真机成功。

当前已建立第一批**离线边界**：`realworld/perception.py` 读取相机参数与 FoundationPose 的 `pose.json`，输出具名物体在对应机械臂 SDK base 下的位姿；`realworld/robot.py` 用注入的 RealMan SDK 读取七轴状态，并在显式运动前预检整个关节轨迹；`realworld/runtime.py` 默认只验证单个已规划运动阶段；`realworld/scene.py` 要求同帧感知和逐实例显式资产 frame 对齐后，才计算现场资产 pose。它们不修改现有 Skill 或仿真源码。可先用历史 task_1 数据检查坐标转换，不连接机械臂：

```bash
python tools/diagnostics/inspect_realworld_snapshot.py \
  --task-dir data/task_1 --side right \
  --objects Bowl/Bowl_0 Microwave/Microwave_0 \
  --output /tmp/task1_observed.json
python -m pytest tests/realworld -q -p no:cacheprovider
```

诊断报告中的 `pose_frame_verified=false` 表示历史 `pose.json` 没有记录它对应的相机帧号；数值可以用于离线核对，**不能作为实时执行依据**。实时流程要让姿态结果带上采集帧号、时间戳和相机 ID，并在规划前设置 `require_matched_frame=True`、检查帧龄。`right_extrinsic_matrix` 是 `T_right_sdk_camera`；物体结果按 `T_right_sdk_object = T_right_sdk_camera @ T_camera_object` 得到。左臂或双臂任务还需显式标定各 SDK base 与任务世界坐标之间的变换，不能直接沿用右臂矩阵。

后续按以下顺序逐项验收；每一步不通过就保留记录并停止，不自动回 home 或跳过失败阶段：

1. **机器人与感知。** 对多组关节角核对 SDK、URDF/cuRobo 的关节顺序、法兰与 TCP；验证夹爪开合/抓力标定、相机外参、物体 mesh 对齐及门角重新估计。 夹爪 Skill 的几何闭合宽度不等于真机硬件位置命令：抓碗/取碗/抓把手/抓旋钮沿用旧版 `pick_on` 力控夹取，松开使用 `release`；推门前单纯闭指才使用位置命令。感知误差要通过可见的真机配置或人工确认处理，不能暗改 Knowledge 的仿真参数。
2. **现场 plan-only。** 先标定 FoundationPose mesh frame 到仿真 collision 资产 frame，再将同帧实测 pose 送入相应资产和阶段接触规则，检查已知碰撞、已知净空、起点及终点可达性，并保存目标、碰撞快照、轨迹与诊断。此步不下发 SDK 运动。
3. **逐个 Skill 低速真机验证。** 先测无接触运动，再测抓碗、把手拉门、内侧推开、外侧推关、放入/取出和旋钮。每段必须从实测终态继续；记录实际 TCP/关节、门角、物体位移、夹爪状态、接触或滑移证据。旧版门流程以复制的《运行指南》及其实际调用链为基准；把手阶段后重估门角。推门/抓取深度、夹持力、速度等 sim2real 修正只放在 task 的 `realworld` 配置并记录生效值。
4. **串联 Task 与泛化。** 单项通过后再串联“开门→放碗→关门→旋钮→开门→取出并桌面放置→关门”，逐段检查后置条件；最后在声明的摆位扰动和感知误差下统计真机成功率。仿真成功率与真机成功率分别报告。

目前已有同帧现场状态到 cuRobo 碰撞快照的构建函数，以及可分别调用的开/关门、Pick、放入、旋钮、取出、桌面 Place 子任务。程序调用方可用 `gene_agent/realworld/microwave/task.py::run_observed_microwave_subtask` 选取其中一段；放入/桌面 Place 须显式提供人工准备的持碗记录，完整任务仍直接调用相同子任务函数。已有连接现场设备与感知的薄入口 `python tools/run/run_microwave_task1_realworld.py`，默认只预检首段；参数与配置见[真机子任务入口说明](docs/user/microwave/realworld_microwave_entry.md)。合成同帧观测到真实 GPU cuRobo 的简单 `plan-only` 已通过，结果见本轮动态基线（历史材料已本地归档；当前入口见 index.md）；**现场入口本身**尚未经过真实感知与标定下的 GPU 规划或设备执行验收。完整任务由 `gene_agent/realworld/microwave/task.py::run_observed_microwave_task1` 调用同一批函数，并在两次开门后、两次关门前按已验收的 MuJoCo Task1 增加四段“回默认 TCP”的任务级过渡；它们不属于单独的门 Skill。`execute=False` 只预检首段，不沿未执行的预测状态继续。离线可运行相关回归：

```bash
python -m pytest -q -p no:cacheprovider tests/realworld tests/tasks \
  tests/applications/microwave/realworld/task/test_realworld_task1.py
```

多物体同帧 FoundationPose 的文件与返回值适配已见 [开发说明](docs/developer/perception/realworld_same_frame_tracking.md)：假 PoseClient 下可将同一冻结 RGB-D 的 Bowl/Microwave 位姿送入现有碰撞导出；新增真机薄适配可读取两臂关节、两夹爪开口及显式带来源和采样时间的门角、旋钮角，过期或缺失状态会拒绝导出。它们仍需现场设备、人工检查或传感器提供，不能从微波炉根 pose 猜关节角；物体同帧不等于所有设备同时曝光。旧版 Microwave 使用把手 mesh，开门后的把手 pose 不能再代表静止本体；现场薄适配现会拒绝这一已知错误，也能在每次确认柜体未移动时使用显式的本体锚点，旧 Task1 的把手测角与 5° 网格公式已有纯几何接口，同步观察器也可在每次子任务调用时重新采集、跟踪并导出现场碰撞；但门轴/局部 frame 标定、锚点确认、把手跟踪精度和柜体独立跟踪仍未现场验收。真实相机与模型服务尚未验收。现场感知精度、mesh 与碰撞资产 frame 标定、双臂/桌面现场标定、真实 cuRobo 规划、夹爪/门/旋钮的物理后置检查及完整 Task 实机执行仍未验收。薄入口已装配现场观测、机器人 Runtime 和 cuRobo pool；只有在有效现场配置、交互终端及显式 `--execute --yes` 下才进入发令路径，且现场接触和后置检查仍待逐段验收。默认旋钮 profile 的直接末关节动作已接入现场 Runtime，但该旧分支没有 cuRobo 场景碰撞规划，执行前须明确检查旋钮周边路径和接触；现场动作仍未验收。具体门槛见 保守真机接入计划（历史材料已本地归档；当前入口见 index.md），冻结基线见 [开发记录](docs/developer/realworld/realworld_baseline.md)。
