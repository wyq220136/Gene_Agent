## 目标与范围

让微波炉的开门、关门、旋钮、放入碗、取出碗能够独立选择、定位失败，并保留已有真机操作入口。完整 Task 和独立运行复用操作实现，policy 负责次序、观测与恢复，不管理仿真会话或机器人设备。

不是重新开发已有功能，不要求先统一所有 Task/Skill，也不把“能独立运行”解释成无视前置状态直接跳转。当前只有微波炉需要这层任务分解。

## 操作与组合两种粒度

复用现有命名；组合入口只描述组合关系，不复制 Skill 或后端实现。

| 独立选择项 | 语义与前置条件 |
|---|---|
| `open_door` / `close_door` | 复用现有门操作；检查实际门角、机器人状态与路径条件 |
| `rotate_knob` | 复用旋钮操作；场景、门状态、目标与接触条件须满足现有要求 |
| `pick_bowl` | 单独抓碗，输出实际持物状态及可核验的抓取证据 |
| `insert_bowl` | 单独放入、释放和撤离；要求有效持碗证据、门已打开，不能虚构 Pick 成功 |
| `extract_bowl` | 复用已有炉内抓取和携碗撤离语义；保持现有终阶段和证据要求 |
| `place_bowl_on_table` | 单独放到桌面、释放和撤离；核对实际持物状态及前序证据 |
| `load_bowl`（组合） | Pick → Insert；门操作和既有 Task 过渡不吞入此组合 |
| `unload_bowl`（组合） | Extract → 桌面 Place；门操作仍由 Task 或调用者处理 |

默认 TCP 过渡保持现有位置和条件，不能因分组省略。组合内部仍保留原阶段名、记录路径和错误来源。完整任务可通过分组描述调用相同步骤，不强求把原步骤记录改为嵌套树。

每个子任务独立成功不等于全任务成功：必须检查相邻操作的实际状态交接，并做 fresh reset 连续验收。不能因组成 load/unload 就隐藏持物操作内部的失败与恢复条件。

## 先确定状态交接，再提取代码

交接分三类，不能都塞进无约束的 ctx：

| 类别 | 内容与职责 |
|---|---|
| 当前实际状态 | 机器人关节/TCP、夹爪、对象与门状态、时间及观测来源；适配层重新观测，policy 只读允许的语义观测 |
| 操作历史证据 | 抓取/接触报告、辅助夹持标记、开始与终态绑定、模型/对象身份、释放与撤离检查；交给后续操作核验，不把历史成功布尔值当当前成功 |
| 后端运行资源 | MuJoCo runtime、门会话、控制增益、规划器池、缓存与附件同步；由适配层持有和管理，不交给 policy |

仿真与真机共用语义，不强迫使用相同的状态 ID 或证据采集方法。真机使用已有实测观测、现场确认与持物检查；不能要求提供 MuJoCo 接触或 weld 证据。未知、过期、模型不兼容和前置条件不满足须明确返回。

失败后保留当前实际终态；控制参数与资源清理由适配层明确处理，不在 policy 中 reset、恢复历史姿态或默认松爪。对增益修改的恢复须核对所有退出路径，不能在重试时反复叠乘。

复用现有 Operation/Check 结果，补必要的证据引用和运行范围。至少能找到原始错误、具体 Pick/Insert 阶段、实际终态、后置检查、近似/辅助标记及视频时间范围。不新增通用 Subtask 基类或第三套执行循环。

## 独立运行的语义

区分两种明确的准备方式，不静默互换：

1. **从当前已准备状态运行**：执行前核对前置条件；不满足则停止并说明缺少什么。真机独立操作沿用该模式。
2. **仿真从 fresh reset 执行必要前缀**：按原 Task 流程完成准备，再运行指定子任务并停止。明确记录前缀与目标子任务，局部成功不写成完整 Task 成功。

真机不自动照搬仿真的准备前缀。是否执行完整任务或所选操作由已有 CLI 和现场配置明确控制；保持原执行确认和检查机制。只检查配置/只规划的结果不能宣称已真机执行。

Insert 与 Place 的已有人工持物准备继续保留；其证据是否满足同一操作的检查由现场适配核验，不制造仿真式的前序报告。首轮不扩展现有门 checkpoint，不承诺任意 Task 中途恢复。

## 文件与接口方向

只在 `gene_agent/tasks/policies/microwave_task/` 内先增加一份适量的 `subtasks.py`，记录已有独立操作和组合关系；内容明显增大后再按职责分目录。`policy.py` 保留完整任务顺序、过渡及决策。

仿真操作从 `simulation.py` 的闭包分派中按需提取，但暂不做全部目录迁移；真机继续使用 `gene_agent/realworld/microwave/`。通过薄适配接同一语义步骤，不把 MuJoCo 逻辑搬进真机，也不宣称两者已共用全部底层实现。

复用现有运行 CLI、Viser 检查器和视频导出，新增选择能力优先加到现有入口。`run_steps()` 的视觉路线本轮不迁移，`run_operation()` 不重写。现有命令与记录兼容；组合名已接入专用 CLI，实际命令见下方实施状态和用户说明。

## 分批实施与验收

### 第一批：load_bowl 打通两种调用方式

- 列清 Pick→Insert 的输入、证据、释放与撤离判据，以及外部前置条件。
- 提取现有操作接线，让完整 Task、load_bowl、单独 Pick/Insert 使用同一实现；保持参数、顺序和原报告路径。
- 仿真支持必要前缀后执行 load_bowl 并停止；对单独 Insert 明确其可接受的状态来源，不暗中补抓取。
- 真机保留现有 Pick/Insert 入口，组合时复用真实 Pick 输出交给 Insert；核对与完整现场 Task 的现有交接一致。无设备时用适配测试验证调用与拒绝路径，不声称硬件成功。
- 验证门未打开/持物证据无效、Pick 失败、Insert 部分执行失败，以及 fresh reset 完整 Task。

### 第二批：补齐微波炉其余选择项

- 复用已有门独立物理入口；检查其与完整 Task 的操作实现和准备差异。
- 为旋钮、Extract、Place 接通缺少的独立 MuJoCo 入口，保留原现场入口。
- 在证据交接和控制增益生命周期核对后增加 unload_bowl 组合。
- Viser 规划与实际回放明确标记来源；定位选择项、阶段和实际失败，不另写一套任务策略。

### 后续按收益决定

checkpoint 扩展、公共循环收敛、独立最终评分、其他 Task 的结构调整分别立项，不自动纳入这两批。已有门 checkpoint 应优先复用，但必须审计完整会话、控制状态和证据兼容性；允许修改后续策略，不因任意代码变动一律拒绝恢复。

## 收益、风险与交付标准

整体属于中等改动，分批执行；第一批主要改微波炉接线、CLI、契约测试和文档，不碰 Skill/motion 算法。具体文件数应在提取调用链后确定，不再用固定文件数替代范围约束。

直接收益是定位失败和局部改代码更容易，并补齐微波炉在仿真/真机下的独立操作路径。执行必要前缀不会节约该部分运行时间；没有实测前不承诺提速倍数。

每批交付应有：

- 可运行命令及准备模式；能力表标明规划、仿真执行、真机适配测试、硬件实测各自状态。
- 同一处摘要定位原始失败、终态和实际视频；原报告保留，无需人工翻多个历史 run。
- 前缀/目标子任务耗时分开；规划/执行时间注明可获取的测量来源，不能用总墙钟冒充。
- 局部成功明确标记范围；固定输入下完整 Task 对照，保持原判据并说明已知评分限制。
- 真实硬件执行仍需另行授权和现场验收；不会因为新增选择入口就宣布可安全直接部署。

## 评审重点

请核对：组合是否确实复用已有操作；交接是否覆盖实际状态、证据与资源三类；单独 Insert/Place 是否保持原能力；真机证据是否被仿真概念污染；第一批是否可避免公共循环和 checkpoint 改造。评审给出代码依据和最小修正，不直接展开全量重构。

## 对未来长任务的适用范围

面向完整 policy 的首批语义单元为开门、放入碗、关门、旋转旋钮、取出并放回桌面；其中真正新增的组合是 load_bowl 和 unload_bowl，其余复用已有操作。微波炉专用单元不冒称能直接用于其他器具。

可复用到新长任务的是组织与执行约定：每个子任务声明前置条件、从实际状态执行、返回后置检查及错误证据；policy 根据新观测选择下一步并控制恢复预算。同一子任务可被多次调用，各次记录具有独立调用标识；不能用函数名覆盖两次开门的记录。既有默认 TCP 过渡仍显式保留。

第一轮用现有顺序流程验证这些约定，不预建任意嵌套 DAG、动态插件或自动任务分解器。未来确有分支、循环或重试需求时由 Python policy 表达，并共享执行预算。仿真恢复不是 policy 的通用能力，最终目标仍由 benchmark 独立验收。子任务局部成功及多次调用均不保证整任务成功。
