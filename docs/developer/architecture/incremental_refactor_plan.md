# 项目渐进重构总计划

> 执行者按阶段推进，实施时使用 executing-plans 工作流；不默认并行开发或提交 Git。每轮只细化并完成当前阶段，验收后更新本页。

**目标：** 固定任务题目与验收，分离 benchmark 和 policy，再逐步收敛稳定的 Skill 库，使新任务主要通过感知、Skill 和少量策略代码完成。

**架构：** benchmark 独立保存场景、初态和判据；`gene_agent/tasks/policies/` 集中保存各任务策略目录，与 tasks 下的公共 runner 等文件分开。现有 Skill、motion 和执行适配先保持原接口，通过小范围接线完成过渡，不同时重写底层。

**技术基础：** Python、现有 Knowledge/Skill 流程、cuRobo、MuJoCo、Viser，以及已存在的现场适配。

**讨论依据：** [Benchmark/Policy/Skill 边界与源码审查](benchmark_policy_skills.md)。

**最新决定（2026-10-30）：先 benchmark → Task，后 Skill。** 用户担心过早重构 Skill 影响已能运行的任务，因此本顺序覆盖此前“先 Pick”的建议。
用户随后授权将当前全部任务统一迁移：微波炉、普通刷、长刷、倒水、舀球。实现已进入新结构，当前正在验证；Skill 接口与操作算法保持。

## 防止重构偏离的检查点

1. 配置拆分后是否读了不同默认值？用解析后有效值与来源对照阶段 0。
2. 原子操作失败后是否丢失实际终态或错误证据？由阶段 2 的失败用例检查。
3. 是否把缺证据/混合成功升级为物理成功？由阶段 1 判据对照检查。
4. 移动文件是否破坏相对资产路径、旧 run 回放和现有 CLI？每阶段保留入口检查和实际回放验证。
5. 共用 Task 是否改变现场步骤或设备行为？仅做离线调用契约验证，硬件实测单独验收。
